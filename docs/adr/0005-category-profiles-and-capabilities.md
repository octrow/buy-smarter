# Category profiles and capabilities instead of category-specific branches

How a category is judged used to hang on three unrelated signals: a stored category type (spec-driven or composition-driven), a phone stem in the first word of the category string (Kimovil), and regexes over the query text (audience, apparel size). A new kind of goods meant new `if` branches in the core, and the category string itself was the free text the parser returned, so one category split into many records ("кроссовки", "мужские кроссовки 42").

We now separate four layers:

1. **Request understanding.** The parse returns a request intent (product, need, open, service, unclear), a restricted flag, the product type, the search phrase and request-level fields. A clarification is returned instead of a ranking when the request is ambiguous: open intent, a need that maps to several product types, more than one product named, a capability missing a required parameter, or an unreadable query. At most two rounds; `no_clarify` skips it. Without an LLM there is no intent detection and only capability rules can ask. Restricted goods (prescription medicines, alcohol, tobacco and vapes, weapons) are searched with a warning, not refused; without an LLM a static word list still flags alcohol, tobacco, vapes and weapons, but not prescription medicines.
2. **Category profile.** Keyed by the product type, with synonyms and an optional parent profile it inherits from. It holds the brand and model books and the category capabilities switched on, each with parameters and who set it. Precedence: user > category learning (LLM, fills parameters) > Jev classifier (on first query, no parameters) > regex and stem fallback without an LLM. Lookup is exact key, then synonyms, then a Jev choice among existing profiles (an LLM when Jev is unsure); no substring matching. The resolved profile records which profile owns each book, and knowledge learned while using a book is saved to its owner.
3. **Core.** One flow for every category: collect, normalize, relevance, dedupe, score, roles, report. No category-specific branches.
4. **Capabilities.** Two levels. Category capabilities live in the profile (composition, benchmark, counterfeit checks, official stores, used market). Request capabilities come from the query (audience, dimensions, compatibility, excluded substances, original only, used only, delivery deadline, origin). Both implement the same optional hooks, each called at the point where today's code does that work: `query` (rewrite constraints and search phrase), `searches` (extra searches), `relevance` (candidates protected from the relevance filter), `reject_listing` (a predicate the core applies to the main pool, OLX ads and official-store offers, after its own listing checks), `hard_features` (adjust required features), `enrich`, `reject_content` (after the feature check), `prepare` + `axis` (pool context, then a score; capability axes come before base axes), `notes` (may replace cons), `section` (report warnings and flags), `clarify`. `ranking/` never imports capabilities: the flow passes it ready weights, axis functions and predicates. A capability axis declares its weight and shifts of the base weights; the core sums, clamps at zero and normalizes to 100. Composition reproduces today's weights exactly (ingredient +25, brand −15, specs −5, popularity −5).

Profiles are stored in the existing `category_knowledge.schema_json`, so no schema migration. Saving merges into the stored record instead of rebuilding it. Old records are read through an adapter (`composition_driven` becomes the composition capability), and until phase 3 is done the old keys are written too, so an older app version still reads them.

## Considered Options

- **Keep the `if` branches, switch them on the profile instead of regexes**: cheapest, but every new capability touches five places in the core again.
- **Capabilities override whole core steps**: flexible, but the core stops being shared and one capability can break the flow for all.
- **One capability level, decided per category by Jev**: audience, size, compatibility and "original only" belong to a query, not a category; a brainstorm of 90 queries put about 35 of them in this group (`docs/research/2026-10-22-query-brainstorm.md`).
- **Per-category weight tables learned by the LLM**: every category would rank differently and tests could not hold it.
- **Refuse restricted goods**: prescription medicines and alcohol are delivered in practice; a warning keeps the answer useful.

## Consequences

Work goes in four phases (`docs/plans/2026-10-22-capabilities-phase1.md` and later plans): phase 1 builds profiles and the capability contract and moves today's behaviour onto them without changing results; phase 2 (request understanding, including budget parsing and moving old long category keys into synonyms) follows; then phases 3 (Jev classifier, auto-learning, GUI toggles, benchmark only with a provider) and 4 (compatibility, dimensions, excluded substances, original only as a counterfeit capability with a strictness parameter, used only as a warning with the OLX section first, a `sources` hook, and moving used market and official stores onto capabilities) run in parallel. Phase 2 goes first because phases 3 and 4 both read the parse fields it adds. Compare mode, unit price, ranking used listings, safety certification, origin and delivery deadlines are out of v1.
