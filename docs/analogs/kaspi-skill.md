## Главное: мы уже впереди по доступу к данным

`MS kaspi/client.py KaspiClient` уже ходит на тот же `POST /yml/offer-view/offers/{id}` с `x-ks-city`, cookie города и referer. Спеки мы берём JSON-эндпоинтом `GET /yml/content/item/product/{id}?c=city` (`parse.parse_specs`). Это надёжнее, чем у K, который парсит HTML (K:796-854). Вежливость тоже лучше: `PoliteClient` даёт семафор, jitter, Retry-After и backoff. У K только фиксированный UA, задержка 0.8 с и ни одного ретрая.

Вывод: брать у них стоит **обработку** данных, а не доступ к ним.

## Детали

- **Тело offers** (K:1101). `cityId`, `id`, `limit`, `page`, `sortOption:"PRICE"`, `zoneId:["Magnum_ZONE1"]`, `installationId:"-1"`, `product{brand, categoryCodes, baseProductCodes, groups, productSeries}`. Блок `product` вырезается из страницы (K:871-897). Наше тело короче: без `product`, `zoneId` и `sortOption`.
- **Город.** Маппинга нет: код по умолчанию 750000000 (Алматы), часовой пояс Asia/Almaty (K:33-36). Код передаётся аргументом CLI или сохраняется в `~/.config/kaspi-skill/location.json`.
- **Доставка** (K:400-424, 935-1000).
  - Карточка поиска даёт только enum `deliveryDuration`: EXPRESS/TODAY → today, TOMORROW → tomorrow, TILL_N_DAYS → «До N дн.».
  - Абсолютная дата есть только в offers: `deliveryOptions{EXPRESS|TO_DOOR|PICKUP}.delivery` (ISO) и `deliveryCost`.
  - Наивная дата считается UTC, затем идёт `astimezone(ZoneInfo(tz))`. Разница с локальным «сегодня» даёт today, tomorrow или later. Подпись вида «14 октября до 18:00», стоимость «бесплатно» или «N ₸».
  - Вариант доставки выбирается так: совпадающий с `deliveryType`, иначе EXPRESS, потом TO_DOOR, потом первый.
  - Лучший оффер — минимум по ключу (группа доставки, цена, −рейтинг продавца).
- **Релевантность** (K:456-570), не больше 100 баллов:
  - 75 × доля совпавших весов токенов. Токен с цифрой длиной ≥3 весит ×3, сравнение идёт по компактной строке, так что «ipx-7» = «ipx7».
  - +10 за бренд в запросе, +15 за попадание модельного токена, +10 если весь запрос входит подстрокой в title, до +10 за совпадения с вариантами запроса.
  - Ниже `min_relevance=20` товар отсекается. Спам отсекается неявно: заспамленный title набирает низкую долю.
- **Жёсткие фильтры.** `--require-term` (OR-группы через `|`), `--require-material`, `--exclude-term`. Причина каждого отсева сохраняется в `rejectedItems`.
- **Дедуп** (K:572-635). Ключ `_canonical_model_key = brand:category:model`, где model — самый длинный токен с цифрой из `baseProductCodes`. Остаются победитель и `listingVariants`.
- **Конфликты спеков** (K:907-932). Узкие и захардкоженные: длина из спеков сверяется с «N-M см» в описании, материал «дерево» — с бук/дуб/бамбук. Код копировать не стоит, брать только идею.

## Что портировать (по ценности и затратам)

1. **Доставка из offers.** Расширить `parse_offers`: `deliveryOptions[*].delivery` и `deliveryCost` → дата в `Asia/Almaty` → группа плюс подпись. Ось «наличие» получает «привезут завтра» вместо enum. Высокая ценность, мало работы.
2. **Модельные токены ×3 и компактное сравнение** (K:489-522) как фильтр релевантности до ранжирования. ~40 строк, ловит чужие модели и варианты.
3. **Дедуп по каноническому ключу модели** (K:572-635). Нужны `baseProductCodes` из карточки поиска.
4. **exclude/require-термы** (K:478-487, 525-545): тривиально, дополняет `required_features`.
5. **Общая проверка конфликтов**: числа и единицы из title против словаря спеков (он у нас уже есть).
6. Опционально: `zoneId` и `sortOption` в теле offers, словарь городов (Алматы 750000000, Астана 710000000). Только если тесты покажут разницу.

Не брать: QR через agent-browser, HTML-парсинг спеков, файл локации.
