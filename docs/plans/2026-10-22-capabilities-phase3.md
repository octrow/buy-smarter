# План: Ф3 — источники возможностей (Jev, автообучение, выбор пользователя)

Фаза 3 по ADR-0005. Этот документ — про то, **кто включает** возможности категории: классификатор Jev на первом
запросе, обучение через LLM (в том числе автоматическое, находка #1) и пользователь в GUI. Плюс правило «benchmark
только при наличии провайдера» (H из штурма). Возможности уровня запроса — Ф4, параллельно с этой фазой.

Начинается после слияния Ф2: опирается на `product_type` как ключ профиля, на профиль и `update_knowledge` из Ф1 и на
`intent` из Ф2 (учим только `product` и `need`).

Цель: первый запрос по новой категории сразу получает разумный набор возможностей, категория выучивается без ручной
команды там, где это безопасно, а выбор пользователя никогда не перетирается и не задевает другие категории.

Версия 2: переписан по независимому ревью (Opus, 2026-10-22). Главное: запись без книг не считается профилем;
выбор пользователя — отдельное поле, слияние возможностей по имени в одной точке; переключатель пишет в профиль
запроса с поимённым наследованием; автообучение только с LLM-разбором, в воркере — отдельная задача taskiq с
лимитами; composition без книги не активна; «нет» от Jev сохраняется; benchmark без LLM — по именительной форме до
первого предлога.

Версия 3: сверен с кодом Ф1 после слияния (main `da1e5e7`). Обновлены «Что есть сейчас» и решения 2, 5, 6, 7, 9: в Ф1
уже есть `setting()` у каждой возможности, composition без книги не включается, а выбор пользователя читается из
`set_by="user"`; уточнено, как вопросы классификатора идут вместе с выбором похожего профиля.

(`services/phone_specs.py:31`).

**Профиль после Ф1:**
- `resolve_profile` (`knowledge/store.py:168`) берёт любую точную запись как `own` и тогда не ищет похожий; при этом
  может один раз вылечить старую копию (`_heal`, пишет в хранилище).
- Похожий профиль ищет `_find_related` (`store.py:399`): все записи кроме своей → владелец синонима (без LLM) → без
  `use_llm` стоп → `_match_category` (Jev, затем LLM). Пустое хранилище — `None` без вызова Jev. Её же зовёт `_heal`.
- `resolve_fields` (`knowledge/profile.py:164`) наследует `capabilities` **целым словарём**.
- Контракт (`capabilities/base.py:49`): базовый класс `Capability` с `ClassVar` `name`, `axis_name` и методом
  `setting(profile, constraints)` — каждая возможность сама решает, включена ли она. Реестр — `capabilities/__init__.py`
  (`REGISTRY`), вызов хуков — `capabilities/flow.py` (`activate`, `ActiveCapabilities`). Возможности: composition,
  benchmark (категории), audience, size (запроса).
- `Composition.setting` (`capabilities/composition.py:379`) уже требует книгу ингредиентов: без книги composition не
  включается.
- `composition_keys` (`profile.py:135`) пишет `set_by="learned"`, а запись с `set_by="user"` не трогает (только
  обновляет книгу, пока пользователь не выключил) — так CLI `learn --file` уже бережёт выбор пользователя.
- Запись — через `update_knowledge` (`store.py:135`, read-modify-write, гонка помечена `ponytail:`); лечение Ф1 берёт
  только записи с `brand_book`, без `capabilities` и без родителя.

## Решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Запись без книг | Правило `has_books(raw)`: есть `brand_book` или `model_book`. Запись без книг (только возможности от Jev, отметки обучения, выбор пользователя) **не профиль** для `own`, для поиска похожего (не попадает в варианты выбора Jev), для переноса Ф2 и для лечения Ф1. Её `capabilities` накладываются поверх найденного профиля по старшинству. Перенос Ф2: старая запись с книгами переименовывается **поверх** записи без книг, возможности сливаются по старшинству. | Иначе запись Jev навсегда отрезает выученный позже похожий профиль и забивает лимит в 255 вариантов. |
| 2 | Выбор пользователя | Поле `CapabilitySetting.user: bool \| None` (включил, выключил, не трогал). Эффективное значение: `user`, если задан, иначе автоматическое `enabled`. Сброс — `user = None`; автоматическое значение и параметры (книга ингредиентов) сохраняются. `set_by` описывает только автоматическое значение (`learned` > `jev`). Ф1 читает выбор пользователя из `set_by="user"` (`composition_keys`); Ф3 переводит эту ветку на поле `user`, убирает `"user"` из `SetBy`, а адаптер `_capabilities` читает старое `set_by="user"` как `user=enabled, set_by="learned"` (пишет его пока никто, но тест на адаптер нужен). | Сброс не теряет выученное. |
| 3 | Одна точка слияния | `update_knowledge` сливает ключ `capabilities` **по имени**: автоматический писатель меняет `enabled`, `params`, `set_by` только если его источник не слабее записанного и **никогда** не трогает `user`. `composition_keys` идёт через неё. Писатели: `learn_category`, CLI `learn` (переводится на `learn_category`, копия удаляется), CLI `learn --file` (слияние с собственной записью, Ф1 решение 6), классификатор Jev, переключатель и сброс в GUI, перенос Ф2, синонимы Ф2, лечение Ф1. Тест на каждого. | `learn --file` при выключенной пользователем composition иначе удалил бы выбор. |
| 4 | Наследование возможностей | Поимённое: возможность ребёнка поверх одноимённой родителя (вместо целого словаря в Ф1 `profile.py:167`). Владелец — по возможности. | Иначе один переключатель у ребёнка прячет все возможности родителя. |
| 5 | Активность composition | Активна = `composition_book() is not None` — в Ф1 уже так (`Composition.setting`); Ф3 добавляет только строку отчёта и тест. Без книги composition не даёт ни весов, ни хуков, ни флага `ingredients_unchecked`; Jev её включение — только строка отчёта «Категория про состав, вещества ещё не изучены». | Иначе «гречка» с ложным «да» Jev получила бы веса состава. |
| 6 | Вопросы Jev | Атрибут возможности `jev_question: str \| None`; у benchmark `None` — вопросы задают провайдеры (решение 9). У возможностей Ф4 (counterfeit, official, used) — `None` (штурм: Jev скажет «да» почти везде). `level`: composition и benchmark — `"category"`, audience и size из Ф1 — `"request"`. `state = {"product_type": …}` и только он — `need` относится к запросу, не к категории. Порог `CLASSIFY_MIN_NOUL` выбирается по живому прогону шага 3 (не «от 0.7»). | Без смешения уровней. |
| 7 | Когда Jev и сколько вызовов | Классификация — внутри разрешения профиля (`ensure_profile`, после `resolve_profile`, до хука `clarify` — порядок Ф2 решения 5), только при `use_llm` запроса и только если для `product_type` нет ни профиля с книгами, ни записи без книг. Вопросы возможностей идут **в том же** `system_one`, что и выбор похожего профиля: `_find_related` получает необязательные вопросы и возвращает ответы; `_heal` вопросов не передаёт. Если похожий профиль с книгами выбран — ответы классификатора отбрасываются (не пишутся). Если до Jev дело не дошло (пустое хранилище, нет записей с книгами, найден синоним без книг) — отдельный `system_one` только с вопросами возможностей. В варианты выбора идут только записи с книгами (решение 1). Сохраняются и «да», и «нет» (`enabled=False, set_by="jev"`) по каждому заданному вопросу; при сбое Jev не пишется ничего. | Один вызов классификатора на новую категорию; «нет» не даёт запасному правилу включить лишнее. |
| 8 | Автообучение — условие | Нет профиля с книгами; `intent` — `product` или `need`; разбор был **через LLM** (`use_llm` запроса); `claude_available()` (без CLI нет веб-поиска — автоматически не учим); `product_type` ≤ 60 символов, буквы, цифры, пробел, дефис; нет отметки `learning_started_at` моложе 15 минут и `learn_failed_at` моложе 24 часов; не превышен лимит `auto_learn_per_hour` (по умолчанию 10, на процесс или Redis). | Учим то, что действительно ищут, и не по мусору. |
| 9 | Benchmark и провайдеры | `BENCHMARK_PROVIDERS: dict[str, …]` (один Kimovil, простой словарь, `ponytail:` класс — когда будет второй). У провайдера `jev_question` («Is this product type a smartphone or mobile phone itself, not an accessory?») и правило без LLM на `product_type`: основы в именительном падеже ед. и мн. ч. целым словом (смартфон, смартфоны, телефон, телефоны) **только в словах до первого предлога** (для, на, к, под, от, с); iphone и айфон — только первым словом. Да: «смартфоны», «мобильный телефон», «iPhone 15» и все «да» из `tests/capabilities/test_benchmark.py`. `Benchmark.setting`: профиль, назвавший benchmark, включает его только с провайдером из реестра. Нет: «чехол на iPhone 15», «чехол для телефона», «держатель телефона», «радиотелефон», «телефонный кабель», «ноутбук». Обучение называет провайдера только из реестра (enum в схеме ответа). | H из штурма; без регрессий нынешних тестов. |
| 10 | Обучение пишет возможности | Промпт `generate_prompt` возвращает список возможностей с параметрами (composition — книга ингредиентов; benchmark — провайдер из реестра). Сохранение через `update_knowledge` по решению 3. Двойная запись старых ключей сохраняется; при `user=False` у composition старая версия приложения увидит `composition_driven` — принять, записать в CHANGELOG. | Решение грилинга 4. |
| 11 | Автообучение — где | Поиск не ждёт обучения. **GUI** — по умолчанию да: после отчёта, если условие выполнено и нет `skipped_llm_steps`; обучение хранится по категории (`dict` категория → задача), статус привязан к своей категории, новый отчёт не ломает чужое обучение; закрытие окна спрашивает и про идущее обучение; по готовности — предложение повторить поиск (`rerun_requested`). **MCP** — да, только при `parse_with_llm=True`: задача в `set()` с done-callback, который логирует исключение (stderr); отчёт: «категория изучается, повторите запрос через несколько минут». **API/воркер** — по умолчанию нет, см. решение 12. **CLI** — после отчёта на TTY: «Изучить категорию сейчас (1–3 мин)? [y/N]» (третий вопрос после уточнения и бюджета), флаг `--learn`; после обучения — предложение повторить поиск. | Решение владельца «по умолчанию да» с поправкой на входы, где LLM по умолчанию нет. |
| 12 | Автообучение в API | Рекомендация ревью: **по умолчанию выключено** (`BUYSMARTER_AUTO_LEARN=false`), потому что API открыт без ключей, знания общие для всех пользователей, а каждый запуск — `opus` с веб-поиском. При включении — отдельная задача taskiq `buysmarter.learn_category` (`.kiq()`), дедуп `SET NX` в Redis, свой таймаут 600 с, лимит в час, не `asyncio.create_task`. Решено 2026-10-22: в API по умолчанию выключено. | Злоупотребление и отравление общих знаний через открытый API. |
| 13 | Переключатели в GUI | Отдельная группа «Как оцениваем эту категорию» на **каждом** отчёте (не только при `knowledge_missing`). Список и подписи — из атрибутов возможности `title` и `level` (только `level="category"`). `QCheckBox` с текстом источника («включено обучением», «выключено вами»), состояние не только цветом, `setAccessibleName`; «Сбросить к автоматическому» неактивна без выбора пользователя. Запись — в профиль `product_type` **запроса** (создаётся, если его нет; если профиль найден как похожий — ему ставится `parent` на найденный), никогда в профиль родителя. Повтор поиска — `rerun_requested`, без автоперезапуска. | Переключатель не меняет чужие категории. |
| 14 | Отчёт | Строка «Как оценивали»: активные возможности и их источник («состав — обучение», «бенчмарк Kimovil — Jev», «состав — выключено вами»), во всех рендерах, в API — новое поле `RecommendOutcome` со значением по умолчанию. | Объяснимость. |
| 15 | Без LLM | Ни Jev, ни автообучения; запасные правила (benchmark — решение 9), без записи в хранилище. | Как в ADR. |
| 16 | Где живёт логика | `capabilities/classify.py`, `capabilities/benchmark_providers.py`, `services/auto_learn.py`; атрибуты `jev_question`, `title`, `level` в `capabilities/base.py` — **первым коммитом**, сразу в main (их ждёт Ф4). | `recommend.py` у предела; Ф4 правит тот же контракт. |

## Порядок работы

Тест первым, коммит на шаг; весь набор и характеризационные тесты Ф1 зелёные после каждого, ожидаемые значения не
меняются (в conftest автообучение выключено и классификатор подменён).

1. **Атрибуты контракта** `jev_question`, `title`, `level` — сразу в main.
2. **Модель профиля:** `has_books`, поле `user`, поимённое наследование, активность composition. Тесты: запись без книг не `own` и не в вариантах похожего; composition без книги = характеризационный сценарий 1 (spec-driven); переключатель у ребёнка не прячет остальные возможности родителя.
3. ✅ **Живой замер Jev** на штурмовом списке (гречка, моторное масло, корм для кошек, подарок, ноутбук, шампунь, крем от акне, смартфон, чехол на iPhone 15) на `jev-1.13.0`: вероятности записать в этот план, выбрать `CLASSIFY_MIN_NOUL`.
   Замер 2026-10-23, `system_one`, вопросы `capability_questions()`; второй список прогнан дважды, разброс ±0.02.

   | Тип товара | composition | Kimovil |
   |---|---|---|
   | гречка, моторное масло, подарок | 0.06 | 0.01–0.04 |
   | корм для кошек | 0.13 | 0.01 |
   | ноутбук, смартфон (composition), чехол на iPhone 15, соковыжималка | 0.01–0.03 | 0.01–0.03 |
   | шампунь | 0.47–0.53 | 0.01 |
   | зубная паста | 0.58–0.59 | 0.01 |
   | шампунь от перхоти | 0.76–0.78 | 0.01 |
   | крем от акне, сыворотка для лица, витамины | 0.84–0.86 | 0.01 |
   | смартфон, кнопочный телефон | 0.01–0.02 | 0.96–0.98 |

   `CLASSIFY_MIN_NOUL = 0.65`: между пограничными (шампунь, зубная паста) и явным «да»; пограничной
   категории composition даст обучение, а не Jev. Kimovil разделяется при любом пороге.
4. **Слияние по имени** в `update_knowledge`; тест на каждого писателя из решения 3; CLI `learn` через `learn_category`.
5. **Провайдеры бенчмарка** и правило без LLM — примеры из решения 9 и `tests/services/test_phone_specs.py:59`.
6. **Классификатор:** одна пачка вместе с выбором похожего; «да» и «нет» сохранены; повторный запрос — ни одного вызова классификатора; сбой — ничего не записано; `use_llm=False` — не зовётся.

## Риски

- **Стоимость автообучения в GUI и MCP.** Настройка `auto_learn`, лимит в час, лог каждого запуска с длительностью; пересмотр после недели живого использования.
- **Гонка read-modify-write** между GUI и MCP в общей SQLite может потерять запись `user`. Рекомендую писать возможности короткой транзакцией в `update_knowledge`; принять остаточный риск (секундное окно).
- **Jev ошибается** на еде и масле: без книги composition не активна (решение 5), а обучение поправит; вероятности шага 3 — основа порога.
- **Параллельная Ф4 правит `capabilities/base.py` и `services/recommend.py`.** Шаг 1 — сразу в main; классификация вставляется только в `ensure_profile`, правки `recommend()` — одна строка вызова.
- **Двойная запись при `user=False`** показывает старой версии приложения включённый состав. Принять до снятия двойной записи.
- **Вылеченная запись Ф1** после отката на старую версию читается как spec-driven (родителя старая версия не знает). Учесть при снятии двойной записи.
