# План: composition-категории — состав, который не проверили, не считается отсутствующим

Шаг 1 из очереди `docs/plans/2026-10-22-logic-map-fixes.md`. Этот документ — только про находки #8, #10, #11, #12
(и про #7 в той части, которая нужна для #10).

**Объём (решено 2026-10-22):** сейчас делаются шаги 1–5 — честная проверка состава, ось, предупреждение (#8, #11, #12).
Шаги 6–8 (#10, #7, лечение записей) ждут архитектуры модулей категории: там решится, как хранятся знания категории.

Цель одной фразой: в лекарствах и косметике «не смогли проверить состав» и «вещества нет» — разные вещи на всех шагах,
а знания заимствованной категории не теряют свой тип.

## Что есть сейчас (2026-10-22)

**Извлечение состава** (`llm/ingredients.py:170`). Сначала Jev, при ошибке — запасной LLM (`_extract_llm`). Если упал и он,
возвращается список пустых `DetectedIngredients`, то есть ответ «ничего не найдено» (`:150-153`). Если LLM пропустил индекс,
у этого кандидата тоже пусто (`:155-158`). Отличить «не нашли» от «не проверяли» вызывающий код не может.

**«Проверено»** (`services/recommend.py:341`): `verified = use_llm and bool(required_substances)`. Флаг не зависит от того,
удалось ли извлечение.

**Жёсткий фильтр** (`ranking/filters.py:149-157`). Вещество «доказанно отсутствует», если среди найденных его нет, а текст состава
есть. При сбое извлечения это верно для каждого кандидата с составом, и `_guard_substance_pool` бросает `NoSubstanceMatch` либо
фильтр выбрасывает правильные товары. Защищённые кандидаты (вещество в названии, `recommend.py:165-178`) проходят фильтр
релевантности, но на жёстком фильтре тоже выпадают.

**Ось ингредиентов** (`ranking/ingredient_axis.py:81-106`). Вещество не найдено и состава нет → 0.3 × 25 = 7.5 и «состав не
подтверждён». Не найдено, а состав есть → 0 и «требуемое действующее вещество отсутствует». Без LLM извлечения нет совсем
(`recommend.py:198`), поэтому честная карточка с составом получает 0, а карточка без состава — 7.5. Так работают MCP и API
по умолчанию.

**Отчёт** (`recommend.py:93`, `cli/report.py:79`, `gui/screens/report.py:161`). `skipped_llm_steps` заполняется, только если
маршрута LLM нет. При явном `--no-llm` и в MCP/API по умолчанию отчёт молчит о том, что вещество не проверялось.

**Синонимы OLX** (`services/matching.py:522-529` → `knowledge/store.py:96-123`). `_persist_learned_aliases` сохраняет знания под
категорией запроса и передаёт `save_knowledge` книгу брендов, книгу моделей и `CANONICALIZE_MODEL`, а `category_type` не передаёт.
Если записи для этой категории ещё нет, тип становится spec-driven, книги ингредиентов нет. Пример: «крем с адапаленом»
заимствует «косметику» и после первого же запуска с LLM и OLX превращается в spec-driven. `resolve_composition` (`store.py:152`)
находит точную запись и дальше к «косметике» не идёт.

**Где искали знания** (`store.py:289-317`). `resolve_books` и `resolve_composition` ищут похожую категорию каждая сама и наружу
не отдают, какую нашли. Вызывающий код не знает, откуда пришли знания, поэтому сохраняет под категорией запроса.

**`generated_by`** (`store.py:119`) перезаписывается при каждом сохранении. После синонимов OLX выученная категория выглядит
так, будто её создала канонизация.

Тесты рядом: `tests/llm/test_ingredients.py`, `tests/ranking/test_ingredient_axis.py`, `tests/ranking/test_substance_filter.py`,
`tests/services/test_recommend_substance.py`, `tests/services/test_recommend_composition.py`,
`tests/services/test_recommend_canonicalize.py`, `tests/knowledge/test_store.py`.

## Решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Как отличить «не проверяли» от «не нашли»? | Новое поле у кандидата: `Candidate.ingredients_checked: bool = False`. Его ставит `True` извлечение — только для кандидатов, по которым пришёл ответ. | Учитывает и полный сбой, и пропущенный индекс у LLM. Признак, общий на весь пул, второй случай не ловит. |
| 2 | Что возвращает `extract_ingredients` при сбое? | `None` у кандидата: `list[DetectedIngredients | None]`. Jev ответил — список ответов. Запасной LLM упал — все `None`. LLM пропустил индекс — `None` у этого индекса. | Минимальная правка сигнатуры; «нет ответа» выражено типом, а не пустым списком. |
| 3 | Вещество в названии | До извлечения: кандидат, в названии которого есть нужное вещество или его аналог (`book.title_needles_for`), получает это вещество в `detected_substances` и `ingredients_checked=True`. Извлечение может дописать концентрацию. | Название — тоже проверка. Такие кандидаты уже защищены от фильтра релевантности (`_substance_confirmed_ids`), теперь их защищает и жёсткий фильтр. |
| 4 | «Доказанно отсутствует» | `_substance_proven_absent` = проверено **и** вещества нет **и** есть текст состава. Флаг `substances_verified` у `rank` и `apply_hard_filters` убираем: решение принимается по каждому кандидату отдельно. | Одно правило вместо двух флагов, которые расходились. |
| 5 | Ось ингредиентов без проверки | Не проверен → 0.3 × вес для всех, минус «состав не проверен: <вещество>?». Есть текст состава или нет — не важно. Проверен и вещества нет → 0 (сюда доходят только кандидаты без текста состава, остальных отсеял фильтр). | Без проверки ось одинакова у всех и не меняет порядок, а пояснение честное. Веса не трогаем: перераспределение — отдельное решение. |
| 6 | Предупреждение в отчёте | Новый флаг `RecommendResult.ingredients_unchecked: bool`: composition-категория и хотя бы у одного кандидата из рейтинга `ingredients_checked=False`. CLI, GUI и MCP показывают строку «Состав не проверен у N из M — вещество не подтверждено». | Пользователь видит, что проверки не было, через какой бы вход ни пришёл. `skipped_llm_steps` не трогаем — он про «нет маршрута». |
| 7 | Куда сохранять синонимы OLX | Под категорией, **из которой пришли** знания. Поиск знаний один раз отдаёт `ResolvedKnowledge(source_slug, brand, model, category_type, ingredient)` — это и есть часть #7. Знания встроенные или не найдены → под категорией запроса, как сейчас. | Синонимы — это модели книги «косметики», а не новой категории. Заодно книги и тип больше не расходятся. |
| 8 | Записи, которые уже испорчены у пользователей | Лечим при чтении: запись без книги ингредиентов и с `generated_by == CANONICALIZE_MODEL` считается «только синонимы». Тип и ингредиенты для неё берутся из похожей категории, если та нашлась и она composition-driven. | Без миграции и без потери синонимов. ❓ **Вопрос к Даниилу:** лечить или достаточно исправить на будущее? Рекомендую лечить: десктоп-пользователи уже накопили такие записи. |
| 9 | `generated_by` перезаписывается | `save_knowledge` сохраняет `generated_by` существующей записи, если она есть. Последний источник правок пишется отдельным ключом `updated_by`. | Иначе правило из #8 примет выученную категорию за «только синонимы». |

## Порядок работы

Каждый шаг — тест первым (RED), потом код, потом коммит.

1. ✅ **Извлечение отличает «нет ответа».** Тест: запасной LLM падает → все `None`; LLM пропускает индекс → `None` у него. Правка `llm/ingredients.py`.
2. ✅ **Флаг проверки и вещество из названия.** Тесты: извлечение упало → `ingredients_checked=False` у всех; вещество в названии → `True` и вещество в `detected_substances`. Правка `ranking/models.py`, `services/recommend.py`.
3. ✅ **Фильтр по каждому кандидату.** Тесты (`test_substance_filter.py`): не проверен, но состав есть → не отбрасывается; проверен, вещества нет, состав есть → отбрасывается; при сбое извлечения `NoSubstanceMatch` не бросается. Убрать `substances_verified`.
4. ✅ **Честная ось.** Тесты (`test_ingredient_axis.py`): два непроверенных кандидата, с составом и без, получают одинаковый балл; минус «состав не проверен» и нет минуса «вещество отсутствует».
5. ✅ **Предупреждение.** Тесты: `--no-llm` в composition-категории → `ingredients_unchecked=True` и строка в отчёте CLI; spec-driven → `False`.
6. ✅ **Один поиск знаний.** *(Сделано в Ф1: `resolve_profile`, шаг 4 плана `2026-10-22-capabilities-phase1.md`.)* Тест (`test_store.py`): категория без записи и похожая «косметика» → `source_slug == "косметика"`, тип и ингредиенты оттуда. `resolve_books` и `resolve_composition` остаются тонкими обёртками для `refresh` и GUI.
7. ✅ **Синонимы — под источником.** *(Ф1, шаг 5: под владельцем книги моделей.)* Тест (`test_recommend_canonicalize.py`): запуск по заимствованной категории с выученным синонимом → запись обновляется у «косметики», новой записи под запросом нет; повторный запуск остаётся composition-driven.

## Отличия реализации (шаги 1–5, 2026-10-22)

- **Проверка по названию работает и без LLM.** Решение 3 не привязано к LLM, поэтому с `--no-llm` кандидат с веществом
  в названии проверен: ось даёт ему 0.7 × 25, остальным — по 7.5. «Одинаковый балл у всех» верен для непроверенных.
  Проверка `NoSubstanceMatch` тоже идёт без LLM, но отсечь может только проверенного, а у проверенных по названию
  вещество есть, так что без LLM она не срабатывает.
- **Проверен, вещества нет, состава нет** → 0, как в решении 5; пояснение «вещество не найдено, состав не указан»
  вместо «отсутствует», минус «состав не подтверждён: <вещество>?» остаётся.
- **MCP** рендерит отчёт через `cli/report.render_markdown`, отдельной правки `mcp_server/server.py` нет. В GUI строка
  идёт в группу «Не удалось проверить» рядом с `skipped_llm_steps`.
- В карте обновлены шаги 16, 17, «Output» и «Known gaps»; шаги 6 и 21 ждут шагов 6–8.
- Живой прогон (шаг 10) не делался.

## Риски

- **Тесты завязаны на `substances_verified`** (`test_engine.py`, `test_recommend_substance.py`). Рекомендую переписать их на `ingredients_checked` у кандидатов, а не держать старый флаг ради совместимости.
- **Вещество из названия даёт ложное срабатывание** («без адапалена», «аналог адапалена»). Рекомендую пока принять: такие названия редки, а `NoSubstanceMatch` честнее срабатывает реже, чем ошибочно. Записать `ponytail:` с порогом пересмотра.
- **Правило лечения (8) затронет настоящую spec-driven запись**, если к ней дописывали синонимы до шага 8 и рядом есть похожая composition-категория. Рекомендую логировать каждое лечение (`knowledge healed: <slug> → <source>`) и смотреть логи первых прогонов.
- **Сигнатура `used_market` меняется** — её вызывает только `recommend`. Проверить grep'ом перед правкой.
