# План: Ф2 — понимание запроса

Фаза 2 по ADR-0005. Этот документ — только про первый слой: что человек хочет купить. Разбор возвращает вид запроса
(intent), флаг ограничений, тип товара и поисковую фразу; неоднозначный запрос получает уточнение вместо рейтинга;
бюджет читается надёжно. Новые возможности (fit, dims, «без X») — Ф4; классификатор Jev и автообучение — Ф3.

Начинается после слияния Ф1: опирается на `resolve_profile`, контракт возможностей (хук `clarify`) и чистый
`recommend()`.

Цель: «подарок для мамы» получает вопрос с вариантами, «ремонт телефона» — ответ «это услуга», «аыавыа» — просьбу
переформулировать, «вейп» — поиск с предупреждением; «мужские кроссовки 42» и «кроссовки» попадают в один профиль;
«до 50 штук» — это 50 000 ₸, а «до 2 м» — не бюджет.

Версия 2: переписан по независимому ревью (Opus, 2026-10-22). Главное: правила бюджета против единиц измерения;
структурный ответ на уточнение вместо дописывания текста; конечный исход на втором раунде; `NeedsClarification` не
наследует `ValueError`; API без нового статуса; таблица потребителей `category` и его удаление последним шагом;
ленивый перенос только для слов аудитории и размера, атомарно.

## Решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Новые поля разбора | В `QueryConstraints`, **все со значениями по умолчанию**: `intent="product"` (`product`/`need`/`open`/`multi`/`service`/`unclear`), `need: str \| None`, `product_type: str`, `search_phrase: str`, `options: list[str]`, `restricted: str \| None` (`rx`/`alcohol`/`tobacco`/`weapon`), `budget_min: int \| None`, `budget_note: str \| None`, `condition: str \| None`. `category` живёт до последнего шага кода: `model_validator` держит `category == search_phrase` в обе стороны. | Старые вызовы и сохранённые в Redis результаты валидируются. |
| 2 | Тип товара и поисковая фраза | `product_type` — короткое каноническое имя без аудитории, размера, совместимости и темы («кроссовки», «шампунь», «зарядка»). `search_phrase` — что отправляем на площадки и по чему ищем вещества («мужские кроссовки», «крем с адапаленом»). Без LLM: `search_phrase` = нынешний `_extract_category` без сленга бюджета; `product_type` = он же без слов аудитории и размера (regex `ranking/audience.py`). Пустой `product_type` от LLM → наивный. Потребители — по таблице выше. | Ключ профиля перестаёт дробиться, вещества не теряются. |
| 3 | Наборы и сравнение | Отдельный intent `multi`: «iPhone 15 или S24», «всё для новорождённого», «собрать ПК» — `options` = названные товары или пункты набора. | Решение 4 штурма: наборы и сравнение в v1 сводятся к «С чего начнём?». |
| 4 | Исключение уточнения | `NeedsClarification(Exception)` — **не** подкласс `ValueError`; каждый вход ловит его **выше** `ValueError`. Несёт `Clarification`: `kind` (`open`, `need`, `multi`, `capability`, `unclear`, `service`), `question`, `options`, `round`, `restricted_note`. Хук возможности `clarify` из Ф1 возвращает `Question` (`question`, `options`); ядро оборачивает его в `Clarification(kind="capability")`. | Иначе пять входов молча превратят уточнение в «нет рекомендации». |
| 5 | Порядок в `recommend()` | Разбор → смысловые поводы (`open`, `need` с несколькими вариантами, `multi`, `unclear`, `service`) → **только потом** `resolve_profile` → хук `clarify` включённых возможностей → сбор. | Не тратить Jev и перенос на запросы, которые не ищем. |
| 6 | Ответ на уточнение | Новый параметр `answer: str \| None` у `recommend()` и всех входов. Ответ совпал с вариантом → `intent=product`, `product_type`/`search_phrase` из ответа, бюджет, город, пол — из разбора исходного запроса; повторный разбор не делается. Свой текст → дописывается к запросу и разбирается заново. | Дописанный текст «… или S24 — iPhone 15» снова дал бы `multi`. |
| 7 | Раунды | `clarify_round` (0, 1, 2) передаёт вызывающий. На раунде 2 или с `no_clarify`: есть варианты → ищем по `options[0]`, `assumed` в результате («Искал: крем для рук»); вариантов нет (`unclear`, `service`, `open`/`need` без вариантов) → конечное `NothingToSearch(ValueError)` с текстом причины; `capability` → ищем без параметра. `need`/`open` с пустыми `options` сразу считаются `unclear`. | Нет бесконечного цикла в CLI и GUI. |
| 8 | Ограничения | `restricted` ставит LLM; без LLM — статический список по границе слова: вейп, жижа, электронн… сигарет…, сигарет…, табак, кальян, вино, пиво, водк…, коньяк, виски, алкогол…, травмат (не «травматолог…»), нож-бабочк…; **без** «пневматическ…». Стоп-контексты: «винный бокал», «пивная кружка», «травматологический», «кальянный уголь» и т.п. — в тесте. Рецептурность без LLM не определяется. Поиск идёт; `RecommendResult.restricted_note` первой строкой отчёта; при уточнении — в тексте вопроса. | Решение владельца: предупреждать, не отказывать. |
| 9 | Без LLM | `intent=product`; если в наивной фразе меньше двух букв — `unclear`. Работают `clarify` возможностей, статический список ограничений и правила бюджета. | Как в ADR, плюс дешёвый отсев мусора. |
| 10 | Бюджет | Порядок проверок: (1) валюта (`$`, `usd`, `€`, `eur`, `руб`, `₽`) → бюджета нет, `budget_note` «бюджет в другой валюте не учтён»; (2) `₸/тг/тенге/теңге`; (3) сленг тысяч `тыс`, `тыщ`, `косар…`, `мың`, а «штук» — **только** после «до/за/бюджет»; «шт» не деньги никогда; (4) `N k/к` — только при N ≥ 10 или после «до/за» («4K» — разрешение); (5) диапазон «30-40 тыс», «от 30 до 40 тыс» → `budget_min`, `budget_max`; (6) голое «до N» — бюджет, только если за числом нет единицы (м, см, мм, кг, г, л, мл, лет, мес, МЕ, Вт, W, дюйм, ", гб, тб, размер, шт, мАч) и нет дробной части; N < 1000 → ×1000. Числа через пробел не склеиваются, кроме групп разрядов «15 000». Найденный бюджет и сленг вычищаются из `search_phrase`. Промпт LLM получает те же правила и примеры. `budget_min` в Ф2 только показывается. | Ни одна единица измерения не становится деньгами. |
| 11 | Ключ профиля и ленивый перенос | `resolve_profile(product_type)`, порядок: точный → синонимы → **перенос старого slug** → Jev/LLM. Перенос: профиля `product_type` нет, есть точная запись под slug `search_phrase`, и разница между ними — только слова аудитории или размера (`audiences`, `_SIZE_RE`) → один `UPDATE category_knowledge SET category=:new WHERE category=:old` (новая функция `repo`, проверка `rowcount`, `IntegrityError` → перечитать), затем старый slug в `synonyms` и `parent` детей обновляется. Иная разница («шампунь-от-перхоти» → «шампунь») — запись не трогаем. Профиль найден, но запись под `search_phrase` тоже есть и отличается только аудиторией/размером → её slug в `synonyms` профиля (книги не сливаем), лог. Пустой `product_type` или `product_type == search_phrase` — переноса нет. | Узкие профили с составом не сливаются в общий; без гонок; Jev не зовётся каждый раз. |
| 12 | CLI | Порядок: разбор → уточнение (TTY: вопрос и варианты с номерами, номер или свой текст → `answer`, `clarify_round+1`; не TTY: печать и код выхода 3) → вопрос про бюджет (если бюджета всё ещё нет) → `recommend()`. Введённый бюджет передаётся в следующие раунды. `NothingToSearch` — код 1. Флаг `--no-clarify`. Код 3 описать в README. | «аыавыа» не должен сначала спрашивать бюджет. |
| 13 | GUI | Исход `Clarification` рядом с `NoRecommendation`: вопрос, кнопки вариантов, поле «свой ответ»; нажатие → поиск с `answer` и следующим раундом. `restricted_note` — над отчётом. «Изучить категорию» учит `product_type`. | По `~/dev/docs/GUI/qt-desktop-guide.md`. |
| 14 | MCP | Параметры `answer`, `clarify_round`, `no_clarify`. `NeedsClarification` → markdown с вопросом, вариантами и инструкцией хосту «спроси человека и вызови снова с answer и clarify_round+1». При `parse_with_llm=False` (по умолчанию) весь прогон без LLM: Ф2 даёт там только бюджет, `unclear` для мусора и `restricted_note`. Docstring просит хоста самому уточнять открытые запросы. | #4 (LLM в MCP по умолчанию) — вопрос плана находок. |
| 15 | API | **Без нового статуса.** Уточнение → `JobStatus.NO_MATCH`, `reason="needs_clarification"`, новое поле `RecommendOutcome.clarification`. `RecommendRequest`: `answer`, `clarify_round` (0–2), `no_clarify`. `RecommendOutcome.constraints` → публичная модель `ParsedRequest` в `jobs.py` с прежним `category` (= `search_phrase`, помечен deprecated) и новыми полями со значениями по умолчанию. `from_result` пробрасывает `assumed`, `restricted_note`, `budget_note`. | Клиенты, ждущие `done/no_match/failed`, не ломаются; внутренняя модель не утекает. |
| 16 | Телеметрия | `_measured` различает исходы `clarify` и `nothing_to_search`. | Иначе уточнения считаются ошибками. |
| 17 | Где живёт логика | `services/understanding.py`: `Clarification`, `NeedsClarification`, `NothingToSearch`, `decide_clarification(...)`, ответ на уточнение, статический список ограничений и тексты предупреждений. Бюджет — `llm/budget.py`. | `recommend.py` у предела 800 строк. |
| 18 | Слова состояния | «б/у», «новый» не уходят в `required_features` (как сейчас) и ставят `condition`; в Ф2 отчёт показывает «Вы искали б/у — смотрите раздел OLX». Ранжирование б/у — Ф4. | Перестаём молча терять слово. |

## Отличия реализации (2026-10-22)

Код Ф1 устроен не так, как предполагал этот план (см. «Отличия реализации» плана Ф1); подстройки и решения по ходу:

- **`Question` — dataclass в `capabilities/base.py`**, хук `clarify(ctx) -> Question | None` у базового класса
  `Capability` (не Protocol); первый вопрос в порядке реестра даёт `ActiveCapabilities.question()` в
  `capabilities/flow.py`. Ядро оборачивает его в `Clarification(kind="capability")` (`ask_capability`).
- **Хуки `query` идут до поиска профиля**, как в Ф1, но после смыслового уточнения: порядок в `recommend()` —
  разбор → ответ и ограничения → смысловое уточнение → город и `read_query` → `resolve_profile` → `activate` →
  вопрос возможности → **только потом** `resolve_sources` (в коде Ф1 источники выбирались до профиля; вопрос не должен
  запускать браузер Ozon).
- **Синхронизация `category ↔ search_phrase`** до шага 10 — `model_validator(mode="before")`; `model_copy` его не
  вызывает, поэтому size и `choose` писали оба поля явно. `category` скрыт из JSON-схемы для LLM (`SkipJsonSchema`).
  На шаге 10 поле и валидатор удалены; публичная `ParsedRequest` держит такой же валидатор для старых записей Redis.
- **`need` без вариантов**: решение 7 говорит «need/open с пустыми options — unclear», но «шампунь от перхоти» (need
  с одним типом, пример промпта) должен искаться. Сделано так: `open` без вариантов — unclear; `need`/`multi` с
  двумя и больше вариантами — вопрос; иначе ищем, если есть поисковая фраза, а без фразы — unclear.
- **`restricted_note` при уточнении** — поле `Clarification.restricted_note`, его показывают все входы над вопросом
  (а не склейка в тексте вопроса).
- **Ответ своим текстом в CLI и GUI**: вход сам дописывает ответ к запросу и сбрасывает `answer` (в CLI — новый
  разбор). Иначе на втором раунде ответ первого терялся бы: `recommend()` дописывает только последний `answer` к
  исходному запросу. MCP и API передают `answer` как есть, дописывает `recommend()`. Ответ-вариант вопроса
  возможности тоже идёт как свой текст (его вариантов нет в `options` разбора).
- **CLI**: `understand_request` (публичный `Clarify` + функция в `services/recommend.py`) зовётся до вопроса про
  бюджет, `recommend()` повторяет его (LLM — из кэша). Терминальная часть — `cli/clarify.py`, иначе `cli/main.py`
  перешёл бы 800 строк. Пустой ответ (Enter) = `no_clarify` для этого вопроса.
- **GUI**: карточка — `gui/screens/clarify.py`; варианты по одному в строке, «Недавние поиски» скрыты, пока виден
  вопрос (экран не прокручивается, иначе кнопки сжимались в 1280×800 — видно на снимке). `answer`/`clarify_round`
  уходят в `recommend()` только со второго раунда.
- **Ленивый перенос (решение 11)**: запись под всей фразой, отличающаяся не только аудиторией/размером
  («шампунь-от-перхоти»), не переносится, **но используется как есть**, если под типом товара профиля нет — иначе
  запрос, который до Ф2 находил свой профиль точным slug, потерял бы его. «Голый» размер одежды («кроссовки 42»)
  тоже считается размером (`bare_product_type` в `ranking/audience.py`). Jev/LLM получает тип товара, не фразу.
- **Ключ кэша LLM** версию промпта не поднимает: промпт входит в ключ (`cache_key_for`), новый промпт — новые строки.
- **Решение 16**: исходы телеметрии `clarify` и `nothing_to_search`.
- **Шаг 10**: в `src`/`tests` после grep остаются не поля разбора — колонки БД (`CategoryKnowledge.category`,
  `Product.category`), `CategoryRefresh.category` (отслеживаемая категория), параметр `category=` хелперов
  `services/matching.py`, формат лога релевантности и `ParsedRequest.category` в тестах API.
- **Ревью по ходу** (вложено в коммиты шагов): `руб` только как валюта («рубашки» не рубли), порог «N k» —
  константа; правило раундов в одной `_may_ask`; тесты на общем `tests/fakes.FakeSource` (добавлено поле
  `searched`); «табакерка» не табак (голый «кальян» по-прежнему даёт предупреждение — дешёвая ошибка); отдельный
  коммит `fix:` для карточки GUI (варианты в столбик, `accessibleName` у поля ответа).
- **Находки живого прогона владельца** (отдельные коммиты `fix:`):
  - Ответ LLM не по схеме валидировался как пустой product (все поля со значениями по умолчанию) и попадал в кэш:
    «подарок для мамы» искал «». Теперь LLM отвечает в `ParsedQuery` (`intent` и `search_phrase` обязательны;
    новое имя схемы — новый ключ кэша), а product с пустой фразой — `unclear`.
  - «крем с адапаленом» потерял composition: Jev сравнивал голый «крем». Ключ остался типом товара, но Jev и
    запасной LLM видят поисковую фразу.
  - Бюджет, который LLM пропустил («до 50 штук»), берут правила `llm/budget.py` (если нет ни `budget_max`, ни
    `budget_note`).
  - Голый размер («мужские кроссовки 42») уходит из фразы, когда размер известен, иначе ленивый перенос не срабатывал.
- **Длина функций**: `recommend()` в `services/recommend.py`, CLI-команда `recommend` и MCP-инструмент `recommend` и
  до Ф2 были длиннее 50 строк (сигнатура с опциями и докстринг); Ф2 добавила параметры и обработку исходов.

## Вне этого шага

- Хук `clarify` у конкретных возможностей (шины без размера, авто без года) — Ф4; в Ф2 только механизм.
- Сравнение «A или B» с итогом «кто лучше», наборы целиком, перевод валют, `budget_min` как фильтр, ранжирование б/у.
- Казахский и английский в наивном разборе (без LLM).
- Включать LLM в MCP и API по умолчанию — вопрос #4 плана находок.

## Риски

- **Новый промпт меняет разбор существующих запросов.** Кэш LLM ключуется именем схемы и пересчитывает строки, которые не проходят валидацию (`llm/cache.py:55`, `llm/adapter.py:305`); промпт тоже меняется. Рекомендую поднять версию промпта в ключе кэша и сравнить `search_phrase` со старой `category` на запросах живого прогона Ф1.
- **LLM слишком часто ставит `open`, `need` с вариантами или `multi`.** Рекомендую в промпте правило «уточнять, только если без ответа поиск — гадание» с антипримерами и лог каждого уточнения; `ponytail:` с порогом пересмотра после 50 живых запросов.
- **Статический список ограничений ловит лишнее.** Ошибка тут — лишнее предупреждение, не отказ; стоп-контексты в тесте, дополнять по логам.
- **Правило бюджета режет настоящий бюджет** («до 3 тыс» — тыс, не единица; «до 2000 за пару»). Рекомендую список единиц только из решения 10 и тесты на обе стороны каждой.
- **Удаление `category` задевает 22 тестовых файла и характеризационные тесты Ф1.** Отдельный последний шаг кода; до него поля синхронизированы валидатором.
