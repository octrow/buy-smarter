# План: compose, GHCR, Helm + kind, OpenTelemetry/Prometheus

Шаги 2–5 цепочки флагмана: ~~Dockerfile~~ → **compose «всё в одном» → образ в GHCR → Helm-чарт + kind-smoke в CI →
OpenTelemetry/Prometheus** (общий план — в личных заметках автора). Шаг 1 (multi-stage Dockerfile)
закрыт, см. `2026-10-16-dockerfile.md`. Каждая фаза ниже — отдельный коммит с зелёным CI; следующая опирается на
предыдущую. Реального облака нет: k8s проверяется только в kind внутри CI.

## Что есть сейчас (2026-10-16)

- `Dockerfile`: цели `runtime` (335 МБ, uid 10001, `HEALTHCHECK` на `/health`, внутри `alembic`) и `browser`
  (headless Chromium для Ozon). CI-job `docker` собирает `runtime` и гоняет smoke, в реестр **не пушит**.
- `docker-compose.yml` поднимает только Postgres 16 (:5434) и Redis 7 (:6380); `make up` используется для разработки.
- В API есть только `GET /health`, без проверки БД. Логи пишутся в файл `~/.cache/buysmarter/logs/` (`logsetup.py`),
  в stdout уходят только WARNING+.
- **Redis объявлен (`REDIS_URL`), но код его не использует** — ни одного импорта `redis` в `src/`.
- `release.yml` по тегу `v*` публикует пакет в PyPI с build provenance; образ в релиз не входит.
- Экшены в workflow закреплены по SHA, у `permissions` по умолчанию `contents: read`.

## Фаза A — compose «всё в одном» ✅ (2026-10-16)

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| A1 | Сервисы | `postgres`, `redis`, `migrate` (тот же образ, `command: alembic upgrade head`), `app` (`depends_on: migrate: condition: service_completed_successfully`, `postgres: service_healthy`) | Миграции один раз до старта приложения — та же схема, что будет Job'ом в Helm |
| A2 | Образ | `build: { context: ., target: runtime }` + `image: ghcr.io/octrow/buy-smarter:${TAG:-latest}` | `docker compose up --build` собирает локально, `docker compose pull && up` берёт из GHCR (после фазы B) |
| A3 | Режим разработки | `app` и `migrate` в профиле по умолчанию; `make up` → `docker compose up -d postgres redis` | Привычный `make up` для работы с хоста не меняется |
| A4 | Конфиг | `env_file: .env` с `required: false`; `DATABASE_URL`/`REDIS_URL` переопределены на имена сервисов (`postgres:5432`) | Ключи LLM из `.env`, адреса — внутренние для сети compose |
| A5 | Браузер | Отдельный сервис `app-browser` в профиле `browser` (`target: browser`) | Chromium (+700 МБ) только когда нужен Ozon |
| A6 | Порты | Postgres/Redis наружу только на `127.0.0.1` | Не светить БД с паролем `buysmarter` на все интерфейсы |

Готово, когда: `docker compose up -d --build` с нуля даёт `app` в статусе `healthy`, `curl :8000/health` → 200,
`docker compose run --rm app buysmarter doctor` видит Postgres. CI-job `docker` дополняется шагом
`docker compose up -d --wait` + curl вместо ручного `docker run`.

## Фаза B — образ в GHCR ✅ (2026-10-16)

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| B1 | Где пушим | Новый workflow `image.yml`: push в `main` и теги `v*`; на PR — только сборка без push (job `docker` в `ci.yml` остаётся) | В PR из форков нет токена на запись, и чужой код не должен попадать в реестр |
| B2 | Имена и теги | `ghcr.io/octrow/buy-smarter` (runtime) и тот же репозиторий с суффиксом `-browser` у тегов. Теги через `docker/metadata-action`: `sha-<short>`, `main`, на релизе `X.Y.Z`, `X.Y`, `latest` | Один пакет в GHCR; `latest` — только релизы, не каждый коммит в main |
| B3 | Платформы | Только `linux/amd64` | arm64 через QEMU с Playwright собирается в разы дольше; добавить, когда понадобится |
| B4 | Права | `permissions` на уровне job: `contents: read`, `packages: write`, `id-token: write`, `attestations: write`; логин через `GITHUB_TOKEN` | Минимум прав, без PAT |
| B5 | Подпись | `actions/attest-build-provenance` с `push-to-registry: true` | Тот же механизм, что уже у PyPI-релиза; проверка — `gh attestation verify oci://…` |
| B6 | SBOM и скан | `sbom: true`, `provenance: mode=max` в build-push; Trivy по `sha-` тегу в `security.yml`, падать на CRITICAL | Закрывает опциональный пункт шага 1 |
| B7 | Версия в label | `build-args: VERSION=${{ steps.meta.outputs.version }}` | `ARG VERSION` уже есть в Dockerfile |
| B8 | Видимость | Пакет публичный, привязан к репо через `org.opencontainers.image.source` (уже в Dockerfile) | `docker pull` без логина; ссылка на пакет на странице репо |

Отличия реализации: Trivy (`aquasec/trivy:0.75.0` по digest, без trivy-action — у него в марте 2026 подменяли теги)
запускается в `image.yml` по digest только что собранного образа, а не в `security.yml`; HIGH печатаются, падение — на
CRITICAL с фиксом. Кэша слоёв в `image.yml` нет, как и в `release.yml`: отравленный кэш попал бы в образ.

Готово, когда: после merge в main в GHCR есть `sha-…` и `main`; после тега — `X.Y.Z` и `latest`; `gh attestation
verify` проходит; README получает бейдж/строку `docker pull ghcr.io/octrow/buy-smarter`.

## Фаза C — Helm-чарт и kind-smoke в CI ✅ (2026-10-16)

### Нужно в приложении до чарта

- `GET /ready`: `SELECT 1` через движок из `db/`, 503 при недоступной БД. `/health` остаётся liveness без
  зависимостей — иначе упавшая БД перезапускает все поды по кругу.
- Логи в stdout: переменная `BUYSMARTER_LOG_TO_STDOUT=1` (или аналог в `logsetup.py`) — в k8s файл в эфемерном
  томе никто не прочитает. В образе включена по умолчанию.

### Чарт

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| C1 | Где | `deploy/helm/buysmarter/` (`apiVersion: v2`, `appVersion` = версия пакета) | Рядом с кодом, версии идут вместе |
| C2 | Объекты | `Deployment`, `Service` (ClusterIP :8000), `Secret` (или `existingSecret`), `ServiceAccount` (`automountServiceAccountToken: false`), `Job` миграций, опционально `Ingress`, `HorizontalPodAutoscaler`, `PodDisruptionBudget`, `ServiceMonitor` — все опциональные выключены | Минимальный набор, который реально нужен; остальное включается флагом |
| C3 | Миграции | `Job` с аннотациями `helm.sh/hook: pre-install,pre-upgrade`, `hook-delete-policy: before-hook-creation,hook-succeeded` | Решение №6 шага 1: миграции один раз перед раскаткой, не в каждом поде |
| C4 | БД | Чарт **не ставит** Postgres: `database.url` или `database.existingSecret`. В kind-smoke Postgres — простой манифест `postgres:16` из `deploy/kind/` | Сабчарт Bitnami после смены их политики образов (2025) — лишний риск; в проде БД всё равно managed |
| C5 | Redis | В чарт не входит, пока код его не использует (см. риски) | Не деплоить мёртвый сервис |
| C6 | Безопасность пода | `runAsNonRoot: true`, `runAsUser: 10001`, `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`; `emptyDir` на `/home/app/.cache/buysmarter` и `/tmp` | Проходит Pod Security Standard `restricted`; числовой uid в Dockerfile уже под это |
| C7 | Пробы | liveness `/health`, readiness `/ready`, startup `/health` с запасом | См. выше |
| C8 | Ресурсы | requests `100m/256Mi`, limits `memory: 512Mi` (без CPU limit) | Стартовые значения; уточнить по метрикам фазы D |
| C9 | Образ | `image.repository: ghcr.io/octrow/buy-smarter`, `image.tag` по умолчанию `appVersion`, `image.digest` опционально | Тег из релиза, digest — для неизменяемого деплоя |
| C10 | Тест чарта | `templates/tests/test-health.yaml` (`helm test`: под с `python -c urllib…` на `/ready`) | Проверка из кластера, а не только port-forward |

### CI-job `helm` (в `ci.yml`)

1. `helm lint` + `helm template … | kubeconform -strict -summary` (схемы k8s, без кластера).
2. Сборка образа `runtime` (кэш `type=gha`, как в job `docker`), `helm/kind-action` → кластер,
   `kind load docker-image buysmarter:ci` — без GHCR, поэтому работает и на PR из форков.
3. `kubectl apply -f deploy/kind/postgres.yaml` + `kubectl wait --for=condition=ready`.
4. `helm install buysmarter deploy/helm/buysmarter --set image.repository=buysmarter --set image.tag=ci --wait --timeout 3m`
   (миграции идут pre-install хуком).
5. `helm test buysmarter`; `kubectl port-forward` + curl `/health`, `/ready`, `/metrics` (после фазы D).
6. `helm upgrade` с тем же релизом — хук миграций идемпотентен, поды раскатываются без ошибок.
7. При падении: `kubectl describe pods`, `kubectl logs` всех подов и Job'а в лог job'а.

Отличия реализации:
- Логи: `BUYSMARTER_LOG_FILE=-` (без файла, INFO в stderr) задаётся в `values.yaml` чарта, а не в образе — иначе
  `docker run … buysmarter recommend` засыпал бы терминал INFO-строками.
- Secret чарта при включённых миграциях — тоже хук (weight -10): pre-install Job стартует раньше обычных ресурсов и
  иначе не нашёл бы `DATABASE_URL`. Цена: после `helm uninstall` Secret остаётся, удалять вручную.
- ServiceMonitor не сделан здесь — он в фазе D (D8).
- Шаги smoke вынесены в `deploy/kind/smoke.sh`, чтобы его можно было прогнать локально против своего kind.

Готово, когда: job `helm` зелёный на PR; `helm template` проходит kubeconform; поды проходят PSS `restricted`
(метка `pod-security.kubernetes.io/enforce=restricted` на namespace в kind); README получает раздел «Kubernetes».

Публикация чарта (OCI в GHCR `oci://ghcr.io/octrow/charts`) — по желанию на релизе, в `image.yml`; не обязательна.

## Фаза D — OpenTelemetry и Prometheus ✅ (2026-10-16)

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| D1 | Подход | OpenTelemetry SDK как единый API; метрики отдаются в Prometheus-формате на `GET /metrics` (`opentelemetry-exporter-prometheus`), трейсы — через OTLP, только если задан `OTEL_EXPORTER_OTLP_ENDPOINT` | Один инструментарий на метрики и трейсы; без коллектора всё работает, с коллектором — добавляются трейсы |
| D2 | Автоинструментация | `opentelemetry-instrumentation-fastapi`, `-httpx`, `-sqlalchemy` (asyncpg-движок), в коде при создании `app`, не через `opentelemetry-instrument` | Явная настройка видна в коде и тестируется; HTTP к Kaspi/OLX и SQL попадают в трейсы |
| D3 | Доменные метрики | `buysmarter_recommend_duration_seconds` (histogram, label `category`), `buysmarter_source_requests_total` (`source`, `outcome`), `buysmarter_llm_calls_total` (`model`, `cache=hit/miss`), `buysmarter_offers_ranked` (histogram) | Это то, что отличает сервис от «FastAPI с /metrics»: видно, какая площадка сломалась и сколько экономит кэш LLM |
| D4 | Где мерить | Инструментация в `services/` и `llm/adapter.py`, не в CLI | Метрики появятся в API, как только там будут эндпоинты (см. риски); CLI их тоже пишет, но не экспортирует |
| D5 | Кардинальность | Без пользовательского текста и цен в label'ах; `category` — из фиксированного списка, иначе `other` | Иначе Prometheus разносит |
| D6 | Конфиг | Стандартные `OTEL_SERVICE_NAME=buysmarter`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_TRACES_SAMPLER`; `BUYSMARTER_METRICS=0` выключает `/metrics` | Стандартные env OTel, ничего своего, кроме выключателя |
| D7 | Compose | Профиль `observability`: `prometheus` (скрейп `app:8000/metrics`), `grafana` с provisioned-датасорсом и одним дашбордом (`deploy/grafana/buysmarter.json`), `otel-collector` → Jaeger или Tempo | `docker compose --profile observability up` — показать на собеседовании за минуту |
| D8 | Helm | `ServiceMonitor` (выключен по умолчанию, для kube-prometheus-stack) + аннотации `prometheus.io/scrape` на поде; `otel.endpoint` в values | Работает и с оператором, и без него |
| D9 | Тесты | Юнит: `/metrics` отдаёт `buysmarter_` метрики после вызова сервиса (in-memory reader); в kind-smoke — curl `/metrics` | Метрики — часть контракта, не «посмотрим в Grafana» |

Перед реализацией сверить API пакетов OpenTelemetry Python по Context7: экспортер Prometheus и инструментация
SQLAlchemy async меняются между минорными версиями.

Отличия реализации:
- Вместо label `category` у длительности подбора — `outcome` (`ok`, `no_match`, `error`): фиксированного списка
  категорий в коде нет, а свободный текст запроса в label'е разнёс бы Prometheus. Размер ранжированного пула —
  `buysmarter_recommend_offers_ranked`.
- Без otel-collector: приложение шлёт OTLP прямо в Jaeger v2 (он принимает OTLP). Коллектор понадобится, когда
  появится второй бэкенд или sampling на стороне сервера.
- HTTP-метрики по стабильным semconv (`OTEL_SEMCONV_STABILITY_OPT_IN=http`): `http_server_request_duration_seconds` с
  label `http_route`. `/health`, `/ready`, `/metrics` не инструментируются.
- Порт Grafana переопределяется через `GRAFANA_PORT` (3000 часто занят).
- Runtime-образ вырос до 346 МБ (OpenTelemetry + protobuf) — в пределах 350, но запаса почти нет.

Готово, когда: `/metrics` отдаёт HTTP- и доменные метрики; с профилем `observability` в Grafana есть дашборд,
в Jaeger/Tempo — трейс запроса с HTTP-вызовами площадок и SQL; kind-smoke проверяет `/metrics`.

## Порядок и коммиты

1. A: `feat: all-in-one compose (app + migrate + postgres + redis)`.
2. B: `ci: publish container image to GHCR with provenance`, затем первый тег релиза с образом.
3. *(рекомендую, см. риски)* HTTP-эндпоинты поверх `services/` — отдельный план.
4. C: `feat: /ready and stdout logs` → `feat: helm chart` → `ci: kind smoke test for the helm chart`.
5. D: `feat: OpenTelemetry metrics and traces` → `feat: observability compose profile and grafana dashboard`.

Каждый шаг — CHANGELOG и строки в README (EN и RU).

## Риски

Риски 1 и 2 закрыты планом [`2026-10-16-recommend-api.md`](2026-10-16-recommend-api.md) (v0.2.0): асинхронный
`POST /recommend` с очередью в Redis. Риск 3 сузился: kind-smoke теперь прогоняет задачу, но проверяет проводку, а не
рейтинг.

1. ✅ **В API только `/health`.** Чарт, метрики и трейсы на сервисе без бизнес-эндпоинтов выглядят пусто: доменные
   метрики из D3 в API просто не появятся. Рекомендую между фазами B и C добавить `POST /recommend` (асинхронно:
   202 + `GET /recommend/{id}`, потому что подбор идёт десятки секунд) и `GET /history` с Pydantic-схемами и
   тестами. Это отдельный план; без него фазы C и D всё равно выполнимы, но демонстрируют меньше.
2. ✅ **Redis не используется.** Он в «стеке вакансии», но в коде его нет. Варианты: дать ему реальную задачу
   (кэш результатов подбора или очередь для асинхронного `/recommend` из п. 1 — естественная связка) или убрать из
   compose и `.env.example`, чтобы не обещать лишнего. Рекомендую первое вместе с п. 1.
3. **Скрейпинг из CI и k8s.** Kaspi отдаёт 429 на IP датацентров, Ozon требует сессию. Smoke в kind проверяет
   только `/health`, `/ready`, `/metrics` — без обращений к площадкам; это нужно явно написать в README.
4. **Время CI.** Job `helm` (сборка + kind) добавит 3–5 минут; кэш `type=gha` общий с job `docker`, при росте —
   запускать kind только при изменениях в `deploy/`, `Dockerfile`, `src/`.
