# Штурм запросов: проверка архитектуры профилей категории и capabilities

2026-10-22. Независимый агент (Opus) придумал 90 запросов (49 групп) и проверил на них предложенную схему:
понимание запроса (intent product / need / open, уточнение) → профиль категории → ядро → capabilities с хуками.
Результат — вход для решения по архитектуре. Решения владельца по разделу 4 фиксируются в плане и ADR, не здесь.

Обозначения. Есть сейчас: COMP (состав), BENCH (бенчмарк), AUD (аудитория), SIZE (размер), CF (подделки),
OFF (официальные магазины), USED (рынок б/у). Новые, которых в схеме нет: FIT (совместимость), DIM (размеры),
UNIT (цена за единицу), SAFE (сертификаты безопасности), ORIG (страна), DLV (срок доставки), AGE (возраст или стадия).

## 2. Дыры, по числу затронутых запросов

1. **Параметры запроса смешаны с параметрами категории (~35).** AUD, SIZE, FIT, DIM, DLV, ORIG, «только оригинал», б/у, «без X» — свойства запроса, не категории. Jev раз на категорию их не выведет.
2. **Размеры не только для одежды (~14).** Шины, матрасы, кольца, диагональ, рама, группа автокресла: жёсткий фильтр, нормализация, иногда перевод (рост/возраст → размер).
3. **Нет intent для отказа (~14).** Услуги, запрещённое и рецептурное, бессмыслица.
4. **Совместимость FIT (~10).** Модель целевого устройства попадает в category; эвристика аксессуаров выкидывает цель; capability нужно своё уточнение.
5. **Цена за единицу UNIT (~10).** Косметика, еда, корм, подгузники, смеси.
6. **Бюджет (~8).** Нет budget_min; «штук», «косарь», «мың», валюты; набор или штука.
7. **Состав «без X» (~6).** Нужен обратный guard: отказ только при доказанном наличии.
8. **Один профиль на запрос не выдерживает (~8).** Сравнение, набор, подарки, need с несколькими типами, франшиза.
9. **Уточнение привязано к intent=open.** Запускать его должна неоднозначность.
10. **Хуков не хватает:** `query` (переписать основной поиск), `clarify` (вопрос capability), `relevance` (своё правило отсева), `price_basis` (цена за единицу), `sources` (OLX как ранжируемый пул).
11. **Ошибки Jev при вопросе на каждую capability:** BENCH «да» без провайдера; COMP «да» для еды, корма, масла → guard остановит прогон; AUD «да» для «подарка»; CF «да» почти везде; SIZE «нет» для шин и колец; USED «да» для еды и лекарств. Category как свободная строка дробит профили.

## 4. Решения для владельца (рекомендации агента)

1. Делить capabilities на уровни категории и запроса? — Да.
2. Уточнение запускает intent или неоднозначность? — Неоднозначность.
3. compare в v1? — Нет; уточнение «какой из двух искать».
4. Наборы? — В v1 сводить к уточнению, ищется один пункт.
5. «Только б/у»: ранжировать OLX? — Позже; в v1 предупреждение и OLX-секция наверху.
6. Запрещённое: отказ или предупреждение? — Отказ с причиной; безрецептурное показывать; перечень сверить с законом РК.
7. Уточнение без LLM? — Нет; отказ по статическому списку работает.
8. Состояние уточнения в HTTP API на сервере? — Нет; ответ дописывается к запросу, номер раунда в повторном запросе.
9. Франшиза (Genshin, Naruto): category или фильтр? — Фильтр по названию на уровне запроса через хук `query`.
